# Harry Potter RAG Chatbot

A Retrieval-Augmented Generation (RAG) chatbot that answers questions about the 7 Harry Potter books, grounded only in the books' actual text.

## Pipeline

```text
Harry Potter.pdf
       │
       │ rag_pipeline.ipynb
       ▼
harry_potter.md + page-level chunks
       │
       │ embed with intfloat/multilingual-e5-large
       ▼
Local FAISS vector index + chunks.pkl
       │
       ▼
rag_api.py (FastAPI)
       │
       ├── 1. Route query with Groq
       │       ├── retrieve
       │       ├── chitchat
       │       └── off-topic
       │
       ├── 2. If "retrieve":
       │       ├── embed query
       │       ├── search FAISS
       │       └── build context
       │
       └── 3. Generate final answer with Gemini
               │
               ▼
          index.html
        (static web UI)
```

Every chunk represents one physical PDF page rather than a paragraph or fixed character window. Each chunk is tagged with its book, chapter, and page number, allowing retrieved answers to point back to the exact page where the information was found.

---

## How It Works

The system follows a standard RAG architecture:

1. The source PDF containing all 7 Harry Potter books is processed in `rag_pipeline.ipynb`.
2. The PDF text is extracted, cleaned, and organized into `harry_potter.md`.
3. The cleaned text is split into page-level chunks.
4. Each page is converted into an embedding using `intfloat/multilingual-e5-large`.
5. The embeddings are stored locally in a FAISS index.
6. The corresponding page metadata and text are stored in `chunks.pkl`.
7. `rag_api.py` runs the FastAPI backend.
8. Groq classifies each incoming query as:

   * `retrieve`
   * `chitchat`
   * `off-topic`
9. For `retrieve` queries, the API embeds the question and searches the local FAISS index for the most relevant pages.
10. The retrieved pages are passed as context to Gemini.
11. Gemini generates a concise answer using only the retrieved context.
12. The static `index.html` frontend sends questions to the FastAPI backend and displays the answer and sources.

# Setup

## 1. Install Dependencies

Install the required Python packages:

```bash
pip install -r requirements.txt
```

This project uses a local FAISS vector store, so no Qdrant server or cloud account is required.

---

## 2. Configure Environment Variables

Copy the example environment file:

```bash
cp .env.example .env
```

On Windows PowerShell, you can instead create a copy manually or use:

```powershell
Copy-Item .env.example .env
```

Then fill in your own API credentials.

| Variable          | Description                                    |
| ----------------- | ---------------------------------------------- |
| `TOP_K`           | Default number of chunks retrieved per query   |
| `EMBEDDING_MODEL` | Sentence Transformer model used for embeddings |
| `GEMINI_API_KEY`  | API key used for final answer generation       |
| `GEMINI_MODEL`    | Gemini model used for final answer generation  |
| `GROQ_API_KEY`    | API key used for query routing                 |
| `GROQ_MODEL`      | Groq model used for query routing              |

Example:

```env
TOP_K=3
EMBEDDING_MODEL=intfloat/multilingual-e5-large

GEMINI_API_KEY=your_gemini_api_key
GEMINI_MODEL=your_gemini_model

GROQ_API_KEY=your_groq_api_key
GROQ_MODEL=your_groq_model
```

> ⚠️ **Never commit your real `.env` file.** It contains live API credentials. Only `.env.example` should be committed to version control.

If API keys have ever been accidentally exposed publicly, rotate them immediately.

# 3. Build the Knowledge Base

Run `rag_pipeline.ipynb` from beginning to end.

The notebook will:

* Extract the text from `Harry Potter.pdf`
* Clean the extracted text
* Identify books and chapters
* Write `harry_potter.md`
* Create page-level chunks
* Generate embeddings using `intfloat/multilingual-e5-large`
* Build the local FAISS vector index
* Save the chunks and metadata to `chunks.pkl`

The final generated vector store consists of:

```text
harrypotter.index
chunks.pkl
```

The notebook should produce the same number of vectors and chunks.

For example:

```text
FAISS vectors: 3584
Chunks:        3584
```

These numbers must match.

### Rebuilding the Knowledge Base

You need to rerun the relevant notebook cells if:

* The source PDF changes
* The text-cleaning logic changes
* The chunking logic changes
* The embedding model changes

If the embedding model changes, the FAISS index must be rebuilt because vectors produced by different embedding models cannot be directly compared.

---

# Why the Embedding Model Has to Match

The embedding model used during indexing must be the same model used when searching.

During ingestion:

```text
page text
    ↓
embedding model
    ↓
FAISS vector
```

During retrieval:

```text
user question
    ↓
same embedding model
    ↓
query vector
    ↓
FAISS search
```

If different models are used, the vectors may have different dimensions or belong to different vector spaces, resulting in retrieval errors or irrelevant search results.

The project currently uses:

```text
intfloat/multilingual-e5-large
```

This is an E5-family embedding model.

E5 models expect different prefixes for documents and queries:

```text
passage: <document text>
```

during indexing, and:

```text
query: <user question>
```

during retrieval.

The notebook and API both follow this convention.

If you change to a different embedding model that does not use the E5 prefix convention, update both the notebook and API accordingly and rebuild the FAISS index.

# 4. Run the API

Start the FastAPI backend:

```bash
python -m uvicorn rag_api:app --reload
```

The API will start at:

```text
http://127.0.0.1:8000
```

You can verify that the backend is running by opening:

```text
http://127.0.0.1:8000/health
```

A successful response should look similar to:

```json
{
  "status": "ok",
  "vector_store": "FAISS",
  "vectors": 3584
}
```

FastAPI's interactive documentation is available at:

```text
http://127.0.0.1:8000/docs
```

You can use the `/query` endpoint directly from the documentation to test the RAG system before opening the frontend.

# 5. Open the Frontend

The chatbot interface is contained in:

```text
index.html
```

`rag_api.py`'s CORS policy only allows requests from `http://127.0.0.1:5500` and `http://localhost:5500` — so **serve this file with a local static server on port 5500** rather than opening it directly as a `file://` page (a raw `file://` origin isn't in the allowlist and every request will fail with a CORS error).

```bash
python -m http.server 5500
```

Then open:

```text
http://127.0.0.1:5500/index.html
```

If you serve it from a different port or tool (e.g. VS Code's Live Server), either match port 5500 or add your server's origin to `allow_origins` in `rag_api.py`.

The frontend sends requests to:

```text
http://127.0.0.1:8000/query
```

The interface also provides a **Ping API** option to verify that the FastAPI backend is reachable.

Once the API is running, enter a Harry Potter question and submit it.

# API Query Flow

For every question, the backend first uses Groq as a lightweight router.

### Retrieve

For a question such as:

```text
Who is Nicolas Flamel?
```

the router returns:

```text
retrieve
```

The API then:

1. Creates an E5 query embedding.
2. Searches the FAISS index.
3. Retrieves the top `K` pages.
4. Builds a context from those pages.
5. Sends the context and question to Gemini.
6. Returns the generated answer and source pages.

### Chitchat

For casual messages such as:

```text
Hello!
```

the router returns:

```text
chitchat
```

The question is handled directly by Groq without performing vector retrieval.

### Off-topic

For unrelated questions, the router returns:

```text
off-topic
```

The API responds:

```text
I can only answer questions about the Harry Potter books.
```

No vector retrieval is performed.

# Evaluation

`rag_pipeline.ipynb` contains two lightweight evaluation sections.

## Precision and Recall

The notebook includes a small set of test questions with hand-picked relevant pages.

For each question:

* **Precision** measures how many of the retrieved pages were relevant.
* **Recall** measures how many of the relevant pages were successfully retrieved.

Example:

```text
Expected pages: {301, 302}
Retrieved pages: {301, 302, 305}

Precision: 0.67
Recall:    1.00
```

The current evaluation set is intentionally small and is intended as a sanity check rather than a comprehensive benchmark.

More labeled test cases should be added for a meaningful evaluation.

---

## LLM-as-a-Judge

The notebook also performs an LLM-based evaluation.

For each evaluation question:

1. FAISS retrieves the relevant pages.
2. Gemini generates an answer using those pages.
3. A second Gemini call evaluates the generated answer.
4. The judge evaluates:

   * Correctness
   * Grounding in the supplied context

The judge returns:

```text
Score: X/5
Grounded: yes or no
Reason: ...
```

This provides a simple way to assess whether the generated answers are both correct and grounded in the retrieved book content.

# Known Limitations

### Page-level Retrieval

Retrieval is performed at the physical PDF-page level.

If an answer spans two consecutive pages, retrieving only one of those pages may result in incomplete context.

Increasing `TOP_K` can help provide more surrounding context.

---

### Router Errors

The Groq router may occasionally misclassify ambiguous questions.

The system expects exactly:

```text
retrieve
chitchat
off-topic
```

Unexpected router output is treated as:

```text
off-topic
```

---

### Embedding Model Size

`intfloat/multilingual-e5-large` is a relatively large embedding model.

The model requires significant memory and takes noticeable time to load, particularly during API startup.

Embedding the approximately 3,584 page-level chunks also takes longer than using a smaller embedding model.

---

### Local FAISS Storage

FAISS is used as a local vector index rather than a hosted vector database.

This makes the project simpler to run and removes the need for an external vector database service.

However, the FAISS index is stored locally and is not automatically synchronized across machines.

The files:

```text
harrypotter.index
chunks.pkl
```

must be available on the machine running the API.

---

### API Keys

The project requires API keys for:

* Gemini
* Groq

These keys should be stored only in `.env` and must never be committed to Git.

If a key is accidentally exposed, revoke and regenerate it immediately.

# Troubleshooting

**"Failed to fetch" in the browser console**
Almost always means the browser never got a response at all — check, in order:
1. Is `uvicorn` actually running? Check its terminal for a startup traceback (e.g. it can fail to start if `harrypotter.index` / `chunks.pkl` don't exist yet — run the notebook first).
2. Open `http://127.0.0.1:8000/docs` directly in a browser tab. If that doesn't load, the API isn't reachable at all — this isn't a frontend problem.
3. Is `index.html` being served from `http://127.0.0.1:5500` (see "Open the Frontend" above)? A CORS error in the console with this exact wording — *"No 'Access-Control-Allow-Origin' header is present"* — almost always means the page's origin isn't in `allow_origins` in `rag_api.py`, most commonly because it was opened as a raw `file://` page instead of through the local server.

**`FileNotFoundError` for `harrypotter.index` or `chunks.pkl` on API startup**
These are generated files, not part of the repo — run `rag_pipeline.ipynb` from top to bottom first (see "Build the Knowledge Base" above) before starting `rag_api.py`.

**`ValueError: FAISS/chunks mismatch`**
`harrypotter.index` and `chunks.pkl` were built at different times (e.g. the notebook was interrupted partway, or one file is from an older run). Delete both and re-run the notebook fully.

**First run is slow / seems to hang**
`intfloat/multilingual-e5-large` (~2GB) downloads from Hugging Face the first time it's loaded — both in the notebook and in `rag_api.py`. Subsequent runs use the local cache and are much faster. Set `HF_TOKEN` in your environment if you hit Hugging Face rate limits on a slow/shared connection.
